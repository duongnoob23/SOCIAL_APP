STEP-01

# Auth Storage — Zustand + MMKV

## Chúng ta vừa làm gì?

Thiết lập một **auth store** dùng Zustand kết hợp MMKV để lưu trữ trạng thái đăng nhập (token, thông tin user) bền vững qua các lần khởi động app.

Gồm 3 phần chính:

1. **MMKV instance** — bộ nhớ lưu trữ vật lý trên thiết bị
2. **Zustand adapter** — cầu nối để Zustand biết cách đọc/ghi vào MMKV
3. **Auth store** — nơi quản lý trạng thái login của toàn bộ app

---

## Tại sao phải làm từng bước như vậy?

### Tại sao dùng Zustand thay vì React Context?

React Context mỗi lần state thay đổi sẽ re-render toàn bộ component tree đang subscribe vào nó. Với auth state — thứ được dùng ở rất nhiều nơi trong app — điều này gây ra performance issue không cần thiết.

Zustand chỉ re-render đúng component đang dùng đến phần state thay đổi, không ảnh hưởng đến phần còn lại.

### Tại sao dùng MMKV thay vì AsyncStorage?

|                  | AsyncStorage     | MMKV                            |
| ---------------- | ---------------- | ------------------------------- |
| Tốc độ           | Chậm (async I/O) | Nhanh hơn ~30x (memory-mapped)  |
| API              | Bất đồng bộ      | Đồng bộ                         |
| Type support     | String only      | String, Number, Boolean, Buffer |
| Phù hợp cho auth | Không lý tưởng   | Có                              |

Auth token cần đọc ngay khi app khởi động để quyết định điều hướng user. Nếu dùng AsyncStorage bất đồng bộ, app phải chờ — dẫn đến flash màn hình hoặc điều hướng sai. MMKV đọc đồng bộ, tránh được vấn đề này.

### Tại sao cần `isHydrated`?

Khi app khởi động, Zustand cần thời gian để đọc dữ liệu từ MMKV và nạp vào store (gọi là **rehydration**). Trong khoảng thời gian đó, `token` và `user` vẫn là `null` — dù thực ra user đã đăng nhập từ trước.

Nếu không có `isHydrated`, `AuthGuard` sẽ thấy `token = null` và điều hướng user ra màn hình login trong tích tắc, trước khi dữ liệu kịp load — đây là lý do gây ra **authentication flash** (màn hình login xuất hiện rồi biến mất ngay).

```
App khởi động
    │
    ├─ isHydrated = false  →  AuthGuard chờ, không điều hướng
    │
    ├─ Zustand đọc MMKV xong
    │
    └─ isHydrated = true   →  AuthGuard kiểm tra token, điều hướng đúng
```

### Tại sao `isHydrated` không được persist?

Nếu `isHydrated: true` bị lưu vào MMKV, lần sau khởi động app Zustand sẽ đọc lên và set `isHydrated = true` ngay lập tức — trước khi rehydration hoàn thành. `AuthGuard` sẽ đọc `token` khi nó vẫn là `null` và điều hướng sai.

`isHydrated` phải luôn bắt đầu là `false` mỗi lần app khởi động, vì vậy nó bị loại khỏi `partialize` — chỉ có `token` và `user` mới được lưu xuống storage.

### Tại sao cần `partialize`?

Mặc định Zustand persist sẽ lưu **toàn bộ state** — bao gồm cả các action function. Dùng `partialize` để chỉ định chính xác những field nào cần lưu, giữ storage gọn và tránh lưu những thứ không cần thiết (actions, `isHydrated`).

### Tại sao `logout` không reset `isHydrated`?

Khi user logout, app vẫn đang chạy — store đã được hydrate từ lúc khởi động rồi. Reset `isHydrated` về `false` sẽ khiến `AuthGuard` nghĩ app đang trong trạng thái khởi động và block điều hướng. Chỉ cần xóa `token` và `user` là đủ.

### Tại sao định nghĩa `AuthUser` thay vì dùng `any`?

`any` tắt hoàn toàn TypeScript — bạn có thể truyền bất kỳ thứ gì vào mà không bị báo lỗi. Khi refactor hoặc backend thay đổi response, lỗi sẽ chỉ xuất hiện lúc runtime thay vì compile time. Định nghĩa rõ `AuthUser` giúp TypeScript bắt lỗi sớm và IDE tự động gợi ý đúng field.

## Luồng hoạt động tổng quan

```
App khởi động
    │
    ├─ useAuthStore khởi tạo với initialState (token: null, isHydrated: false)
    │
    ├─ Zustand đọc MMKV → onRehydrateStorage callback chạy
    │       │
    │       ├─ Có dữ liệu cũ  →  nạp token + user vào store
    │       └─ Không có       →  giữ nguyên null
    │
    └─ setHydrated() được gọi → isHydrated = true
            │
            ├─ token tồn tại  →  AuthGuard cho vào app
            └─ token null     →  AuthGuard đẩy ra màn hình login


User đăng nhập thành công
    └─ setAuth(token, user) → lưu vào store + tự động sync xuống MMKV


User đăng xuất
    └─ logout() → xóa token + user khỏi store + tự động xóa khỏi MMKV
                  (nhớ gọi clearCustomerIOUser() ở đây)
```

- [ ] Gọi `setAuth()` sau khi nhận token từ API login
- [ ] Gọi `logout()` khi user bấm đăng xuất hoặc token hết hạn

## 2. Bước 1 — Auth Store (Zustand + MMKV)

### Tại sao Zustand thay vì React Context?

React Context re-render toàn bộ component tree mỗi khi state thay đổi. Auth state được dùng ở rất nhiều nơi trong app — dùng Context sẽ gây performance issue không cần thiết. Zustand chỉ re-render đúng component đang subscribe vào phần state thay đổi.

### Tại sao MMKV thay vì AsyncStorage?

|                  | AsyncStorage     | MMKV                           |
| ---------------- | ---------------- | ------------------------------ |
| Tốc độ           | Chậm (async I/O) | Nhanh hơn ~30x (memory-mapped) |
| API              | Bất đồng bộ      | Đồng bộ                        |
| Phù hợp cho auth | Không lý tưởng   | Có                             |

Auth token cần đọc ngay khi app khởi động để quyết định điều hướng. AsyncStorage bất đồng bộ khiến app phải chờ và gây flash màn hình. MMKV đọc đồng bộ, tránh được vấn đề này.

### Cấu trúc Store

```typescript
// store/authStore.ts

interface AuthStateData {
  token: string | null;
  user: AuthUser | null;
  isHydrated: boolean; // true khi MMKV đã load xong vào RAM
}

interface AuthStateActions {
  setAuth: (token: string, user: AuthUser) => void; // gọi sau login
  logout: () => void; // gọi khi đăng xuất
  setHydrated: () => void; // gọi bởi onRehydrateStorage
}
```

### Tại sao cần `isHydrated`?

Khi app khởi động, Zustand cần thời gian đọc dữ liệu từ MMKV vào RAM (gọi là **rehydration**). Trong thời gian đó `token` vẫn là `null` dù user đã đăng nhập từ trước. Nếu `index.tsx` đọc `token` lúc này, nó sẽ thấy `null` và đẩy user ra màn hình login — đây là nguyên nhân gây ra **authentication flash**.

`isHydrated` là tín hiệu để `index.tsx` biết khi nào được phép đọc `token`.

```
App khởi động
    │
    ├── isHydrated = false  →  index.tsx chờ, không điều hướng
    ├── Zustand đọc MMKV xong
    └── isHydrated = true   →  index.tsx đọc token, điều hướng đúng
```

### Tại sao `isHydrated` không được persist?

Nếu `isHydrated: true` bị lưu vào MMKV, lần sau khởi động app Zustand đọc lên và set `isHydrated = true` ngay lập tức — trước khi rehydration hoàn thành. `index.tsx` sẽ đọc `token` khi nó vẫn là `null` và điều hướng sai. `isHydrated` phải luôn bắt đầu là `false` mỗi lần app khởi động, vì vậy nó bị loại khỏi `partialize`.

```typescript
partialize: (state) => ({
  token: state.token,   // ✅ lưu xuống MMKV
  user: state.user,     // ✅ lưu xuống MMKV
  isHydrated: false,    // ❌ không lưu, luôn bắt đầu là false
}),
```

### Cách dùng Store đúng — dùng selector

```typescript
// ❌ Sai — subscribe toàn bộ store, re-render khi bất kỳ field nào thay đổi
const { token, isHydrated } = useAuthStore();

// ✅ Đúng — chỉ re-render khi đúng field đó thay đổi
const token = useAuthStore((state) => state.token);
const isHydrated = useAuthStore((state) => state.isHydrated);
```

## 3. Bước 2 — Root Layout

### Vai trò của `_layout.tsx`

File này là **shell** của toàn bộ app — nơi khởi tạo các Provider và load tài nguyên cần thiết trước khi render UI. Nó không chứa logic điều hướng.

### Thứ tự Provider — tại sao quan trọng

```tsx
<GestureHandlerRootView>
  {" "}
  // 1. Native gesture — PHẢI là ngoài cùng tuyệt đối
  <SafeAreaProvider>
    {" "}
    // 2. Cung cấp insets cho toàn app
    <KeyboardProvider>
      {" "}
      // 3. Cần biết safe area để tính toán đúng
      <QueryClientProvider>
        {" "}
        // 4. Data layer, không phụ thuộc UI
        <ThemeProvider>
          {" "}
          // 5. Styling — gần UI nhất
          <Stack /> // 6. UI thực sự bắt đầu từ đây
        </ThemeProvider>
      </QueryClientProvider>
    </KeyboardProvider>
  </SafeAreaProvider>
</GestureHandlerRootView>
```

Mỗi provider phụ thuộc vào thông tin từ provider bên ngoài nó — đây không phải tuỳ ý mà là dependency order.

### Font loading — tại sao dùng `useFonts` thay vì `AsyncFont × 12`

`AsyncFont` load từng font một theo kiểu fire-and-forget, không có cơ chế biết khi nào tất cả font đã sẵn sàng. `useFonts` của Expo load song song tất cả font, trả về `[loaded, error]` để app biết chính xác khi nào được phép ẩn splash screen.

```typescript
const [fontsLoaded, fontError] = useFonts({
  "Gotham-Regular": require("../assets/fonts/Gotham-Book.otf"),
  "Gotham-Bold": require("../assets/fonts/GOTHAM-BOLD.ttf"),
  // ...
});

useEffect(() => {
  // fontError: dù font lỗi vẫn phải ẩn splash, không để app treo mãi
  if (fontsLoaded || fontError) {
    void SplashScreen.hideAsync();
  }
}, [fontsLoaded, fontError]);
```

### Tại sao `QueryClient` khai báo ngoài component?

```typescript
// ❌ Sai — mỗi lần _layout.tsx re-render tạo ra instance mới
// Toàn bộ cache của React Query bị xóa trắng
export default function RootLayout() {
  const queryClient = new QueryClient(); // ← bug nghiêm trọng
}

// ✅ Đúng — khai báo một lần duy nhất ở module level
// lib/reactQuery.ts
export const queryClient = new QueryClient();
```

## 4. Bước 3 — Index (Điều phối luồng)

### Vai trò của `index.tsx`

File này không render UI. Nhiệm vụ duy nhất là chờ store sẵn sàng rồi điều hướng user đến đúng màn hình.

### Tại sao dùng `useRouter` thay vì `<Redirect>`?

`<Redirect>` là component — nó điều hướng **trong quá trình render**, tại thời điểm navigation stack có thể chưa được khởi tạo xong. `index.tsx` là điểm vào đầu tiên của app nên navigator chưa ổn định.

`useRouter` điều hướng bên trong `useEffect` — **sau khi render**, đảm bảo navigator đã sẵn sàng.

```
<Redirect> điều hướng trong render   →  navigator chưa sẵn sàng  →  lỗi hoặc không có gì xảy ra
useRouter  điều hướng sau render     →  navigator đã sẵn sàng    →  an toàn
```

### Tại sao cần kiểm tra `navigationState?.key`?

`navigationState?.key` là tín hiệu cho biết Expo Router đã khởi tạo xong navigation stack. Nếu không kiểm tra, `router.replace()` có thể được gọi trước khi stack tồn tại.

### Tại sao dùng `setTimeout 0ms`?

```typescript
setTimeout(async () => {
  router.replace(token ? "/(main)/story" : "/(auth)/sign-in");
}, 0);
```

`setTimeout 0ms` đẩy việc điều hướng ra ngoài render cycle hiện tại vào microtask queue. Tránh React warning: _"Cannot update a component while rendering a different component"_.

### Luồng đầy đủ của `index.tsx`

```typescript
useEffect(() => {
  if (!navigationState?.key) return; // Navigator chưa sẵn sàng → chờ
  if (!isHydrated) return; // MMKV chưa load xong → chờ

  const timer = setTimeout(async () => {
    router.replace(token ? "/(main)/story" : "/(auth)/sign-in");
    await SplashScreen.hideAsync();
  }, 0);

  return () => clearTimeout(timer);
}, [navigationState?.key, isHydrated, token]);
```

## 6. Những thứ sẽ thêm sau

Nguyên tắc: **chỉ thêm khi thực sự cần**, không setup trước.

| Thêm khi nào                   | Thứ cần thêm                   | Vị trí                                     |
| ------------------------------ | ------------------------------ | ------------------------------------------ |

| Cần ads tracking               | `Facebook SDK`                 | `useEffect` trong root layout              |
| App có đa ngôn ngữ             | `I18nextProvider` + `initI18n` | Root layout                                |
| Màn hình có nhiều bottom sheet | `BottomSheetModalProvider`     | Root layout hoặc group layout              |
